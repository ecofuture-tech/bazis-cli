# bazis-cli 2.5.0

## Features

- `bazis new` builds the whole product: the backend and its frontend made by bazis-front.
  The skeleton has bazis-front in `requirements.txt` and `BS_INSTALLED_APPS` and a section
  on the frontend in `AGENTS.md`; the agent follows the order of the guide of bazis-front:
  `bazis_front init`, the specs of the product in `spec/` (roles, entities, workflows,
  access, scenarios, screens), the backend that satisfies them with the permit roles, the
  statuses and transits declared in `roles.py` and `workflow.py` (applied by `migrate`) and
  the test users of `manage.py e2e_data` (the
  e2e data command recommended by bazis-front), migrate, `bazis_front contract`,
  `front_check` until no errors, the components (`front_catalog`, `bazis_front add`), the screens, the design
  (`bazis_front design`), the end-to-end tests (`bazis_front e2e`, run against the backend)
  and the final checks (`front_status`, `tsc`, lint, the component tests, the build).
- `--no-frontend` builds only the backend, as before.
- **The languages of a product.** A product is in the language of its description and in
  English, the language of the msgids (`BS_LANGUAGES`, `BS_LANGUAGE_CODE`): the agent finds
  the language, or `bazis new --language CODE` (`ru`, `ru-RU`, `pt_BR`: a code of Django,
  matched by its base code) writes it in `project.env` of the skeleton. The rules of the
  agent: English msgids with `gettext_lazy`, the catalogs of the project
  `locale/<language>/LC_MESSAGES/django.po` made, filled and compiled by `manage.py
  bazis_messages` of bazis 2.15 (`make`, the translations in `locale/translations.json`,
  kept in the project, `apply --check`), never by a script that edits the `.po` files nor
  by `makemessages` or `compilemessages` run by the agent (from another directory they
  wrote into and compiled the catalogs of the packages in `.venv`), no text in another
  language in the code, a msgid that two packages translate differently (`bazis.W004`)
  declared with `gettext_noop` in `<project>/translations.py` and translated through
  `bazis_messages` (the catalog of the project wins), a `bazis.W005` reported, and without
  GNU gettext the catalogs reported as not made, never written another way; with a
  frontend, `languages` and `language` in the specs and the texts of the screens through
  `t()` with the dictionaries of the product `src/i18n/<language>.ts`; with bazis-users, a
  user model of the project with `UserLanguageMixin`.
- **The tests never flush the shared Redis**: the `tests/conftest.py` of the skeleton gives
  the cache keys of the tests a prefix of their own, new at every run and in every thread,
  and deletes only them; the rules tell the agent to keep it. The pytest plugin of
  bazis-test-utils 2.5 installs the triggers of the test database and `migrate` (also the
  flush of a test with `transaction=True`) applies the declarations: the rules forbid a
  hand-written `django_db_setup` or fixtures of the roles, statuses and transits.
- **The released stack in the rules.** The roles of bazis-permit are declared in
  `<app>/roles.py` and the workflows of bazis-statusy in `<app>/workflow.py` (2.9.1), never
  created by data migrations; with bazis-ws (2.6.0) the agent publishes with
  `publish_changed()` and routes the socket with `router.register('bazis.contrib.ws.router')`,
  and notifies with `notify` of bazis-notify when the project has it (never a second
  message of bazis-ws), else with `notify()` and `notification()` of bazis-ws; `run_doctor` also checks the data against
  the declarations (bazis 2.13: `permit.W005`, `statusy.W003`, or the info
  `bazis.database` without a database).
- The rules tell the agent to import `bazis.contrib.users.token` in the root router of a
  project with bazis-users that does not register the user routes (`users.E002`).
- **Points and distances in the rules.** A location is a `PointField` (`geography=True`
  when the product measures distances), never two `FloatField`s; what is near is the
  `near` filter and the sort `<field>__distance(<lon>,<lat>)` of bazis 2.15, never a
  distance computed by the project (`point_distance`/`point_within` of
  `bazis.core.utils.geo` in the code).
- The rules: a route set that restricts its objects itself and applies it in its
  `get_queryset` (`FileUploadRouteSet`, the routes of bazis-bg) needs no
  `permit_public = True` (bazis-permit 2.10).
- The evals grade the catalogs of a product in another language complete
  (`bazis_messages status --check`).
- The evals have a task with a description in Russian (`recipes`), graded on the languages
  of the product and its compiled catalog.
- `bazis add` in a project with a frontend exports the contract, fixes the specs, copies
  the components of the new capability and runs the frontend tests; `bazis add
  bazis-front` builds the frontend of a backend.
- `bazis audit` reviews the frontend too: `front_check`, `front_status`, the guides of
  bazis-front, and with `--fix` the generated files, `tsc`, lint, the tests and the
  end-to-end tests.
- `BAZIS_FRONT_REQUIREMENT` replaces the requirement of bazis-front in a new product (a
  path to a wheel or a checkout, or a URL), to try a version that is not on PyPI; uv
  builds it again (`--refresh-package`) instead of reusing the build of an older commit.
- **`bazis new` creates the database of the project.** After `.venv`, the settings of the
  project (`.env`, the `BS_DATABASES__DEFAULT__*` variables of the environment) are read
  by its Python and the database is created on PostgreSQL when it is missing, with the
  extension PostGIS for the PostGIS backend (the default); an existing one without tables
  is kept. One with tables (other than those of an extension) is reported as the data of
  another project, not as ready: set another `BS_DATABASES__DEFAULT__NAME` in `.env`, and
  the agent does not migrate it; so is one that exists but could not be opened (no
  `CONNECT`, a timeout): check the access to it or choose another name. A failure of the extension is told apart from the
  database (`PostGIS is not installed in it: <error>`). When PostgreSQL cannot be reached
  (5 seconds) or the database cannot be created, it says why and goes on. The task tells the agent what was done; the rules tell it never to drop or
  recreate the database and, after the first `migrate`, to add migrations instead of
  generating the applied ones again (every trial agent created the database itself, one
  dropped it to regenerate its migrations). The evals create it the same way.
- The rules of the agent: a package is added with its installed release as the minimum
  (below); temporary files go to `.scratch/` of the project
  (in the `.gitignore` of the skeleton), not `/tmp`; no password or other secret in the
  messages or the summary, only where it is set; a database the agent creates is reported.
- The evals have a task with a frontend (`helpdesk`), graded on the specs against a fresh
  contract, the generated files, the build, the lint and component tests, and the
  end-to-end tests against the backend; the warnings of bazis-bg and bazis-front are
  graded with those of the other packages (only warnings: the infos of a database that
  does not exist yet are not).

- **Guides by sections, the sources only for a gap.** The rules tell the agent to read the
  introduction of a guide and then a section (`package_guide(name, section)`) when a step
  needs it, never all of them in advance (`bazis new` read the guide of bazis-front in 16
  pages before the first line of code), and not to read the sources of the packages (in
  `.venv`, the vendored copies, checkouts) unless the guide lacks the fact, which it then
  names in the section Guide gaps of the summary.
- **One round of the final checks.** `run_doctor` runs after a change; the final checks
  (`run_doctor`, the tests and those of the frontend: `front_check`, `front_status`, `tsc`,
  lint, the component tests, the build and the end-to-end tests) run once after the last
  change, and after a fix only those that failed. The steps of a frontend are those of the
  guide of bazis-front, with what bazis-cli adds to them, not a copy; the screens are looked at once in screenshots (into
  `.scratch/`), one pass before the final checks; a test that fails only sometimes gets one
  attempt at a fix, then goes to Left for you.
- **A summary in fixed sections:** Built, Packages, Run, Outside the files, Left for you,
  Guide gaps.
- **The facts of a run in `.bazis/run.json`.** Every command writes the turns, the cost, the
  duration, the usage of the tokens and the calls of each tool of its run to the project,
  for the measurements of the runs (`.bazis/` ignores itself in Git).
- **The ports of a project.** `bazis new` chooses free ports for the backend, the dev server
  of the frontend and that of the end-to-end tests and keeps them in `.bazis/ports.json`;
  the task gives them to the agent, which writes `BAZIS_API_URL` in `frontend/.env.local`
  and runs the servers and `npm run e2e` (`E2E_PORT`) on them, never on 8000 and 5173 that
  other projects use (every trial lost turns on a busy port). `bazis add` and `bazis audit
  --fix` of a product choose them when the project has none.
- **The files of a project in the project.** The `.env` of the skeleton sets
  `BS_MEDIA_ROOT` and `BS_STATIC_ROOT` to `media/` and `static/` of the project (ignored by
  Git), not `/tmp/media` and `/tmp/static` shared by every project.
- **The minimums of the installed releases.** After installing `.venv`, `bazis new` raises
  the minimums of `requirements.txt` and `requirements-dev.txt` to the installed releases
  (`X.Y.Z`, also of a build after a release such as `2.16.0.post1.dev3`; a pre-release
  keeps the minimum): the guides the agent reads and the API it uses are those of the
  installed versions. The rules tell the agent to give a package it adds its installed
  release as the minimum, never `catalog_version` (a catalog built from checkouts has
  versions such as `2.15.1-12-gc4e2997 (clone)`, and the agent wrote a lower minimum than
  the API it used).

## Breaking changes

- `bazis new` needs Node.js 22.12 or newer with npm unless `--no-frontend`: without them
  it stops before writing anything.
- New projects need bazis 2.15.0 (the language of each request, `bazis.W004`, `W005`, the
  database checks of `bazis_doctor`, `bazis_messages`, the points written as GeoJSON and
  sorted by the distance), the latest release, which bazis-front also needs, and
  bazis-test-utils 2.5.1 (its pytest plugin) in `requirements-dev.txt`.
- bazis-cli and new projects need bazis-mcp 2.4.5 (the tools `front_check`,
  `front_status`, `front_catalog`, and the installed packages read from the Python of the
  project at every call: before, the server run by bazis-cli reported the packages of the
  Python of the CLI); a new product needs bazis-front.
