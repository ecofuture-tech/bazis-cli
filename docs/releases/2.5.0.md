# bazis-cli 2.5.0

## Features

- `bazis new` builds the whole product: the backend and its frontend made by bazis-front.
  The skeleton has bazis-front in `requirements.txt` and `BS_INSTALLED_APPS` and a section
  on the frontend in `AGENTS.md`; the agent follows the order of the guide of bazis-front:
  `bazis_front init`, the specs of the product in `spec/` (roles, entities, workflows,
  access, scenarios, screens), the backend that satisfies them with the permit roles, the
  statuses and transits declared in `roles.py` and `workflow.py` (applied by `migrate`) and
  the test users of `manage.py e2e_data` (the
  e2e data command recommended by bazis-front), migrate, `bazis_front contract`,
  `front_check` until no errors, the components (`front_catalog`, `bazis_front add`), the screens, the design
  (`bazis_front design`), the end-to-end tests (`bazis_front e2e`, run against the backend)
  and the final checks (`front_status`, `tsc`, lint, the component tests, the build).
- `--no-frontend` builds only the backend, as before.
- **The languages of a product.** A product is in the language of its description and in
  English, the language of the msgids (`BS_LANGUAGES`, `BS_LANGUAGE_CODE`): the agent finds
  the language, or `bazis new --language CODE` (`ru`, `ru-RU`, `pt_BR`: a code of Django,
  matched by its base code) writes it in `project.env` of the skeleton. The rules of the
  agent: English msgids with `gettext_lazy`, the catalog of the project
  `locale/<language>/LC_MESSAGES/django.po` made with `makemessages` and compiled (the
  skeleton has `locale/`, the first of `LOCALE_PATHS`: without it `makemessages` wrote the
  msgids of the project into the catalog of a package in `.venv`), no text in another
  language in the code, `bazis.W004` and `bazis.W005` clean; with a
  frontend, `languages` and `language` in the specs and the texts of the screens through
  `t()` with the dictionaries of the product `src/i18n/<language>.ts`; with bazis-users, a
  user model of the project with `UserLanguageMixin`.
- **The tests never flush the shared Redis**: the `tests/conftest.py` of the skeleton gives
  the cache keys of the tests a prefix of their own, new at every run and in every thread,
  and deletes only them; the rules tell the agent to keep it. The pytest plugin of
  bazis-test-utils 2.5 installs the triggers of the test database and `migrate` (also the
  flush of a test with `transaction=True`) applies the declarations: the rules forbid a
  hand-written `django_db_setup` or fixtures of the roles, statuses and transits.
- **The released stack in the rules.** The roles of bazis-permit are declared in
  `<app>/roles.py` and the workflows of bazis-statusy in `<app>/workflow.py` (2.9.1), never
  created by data migrations; with bazis-ws (2.6.0) the agent publishes with `notify()`,
  `notification()` and `publish_changed()` and routes the socket with
  `router.register('bazis.contrib.ws.router')`; `run_doctor` also checks the data against
  the declarations (bazis 2.13: `permit.W005`, `statusy.W003`, or the info
  `bazis.database` without a database).
- The rules tell the agent to import `bazis.contrib.users.token` in the root router of a
  project with bazis-users that does not register the user routes (`users.E002`).
- The evals have a task with a description in Russian (`recipes`), graded on the languages
  of the product and its compiled catalog.
- `bazis add` in a project with a frontend exports the contract, fixes the specs, copies
  the components of the new capability and runs the frontend tests; `bazis add
  bazis-front` builds the frontend of a backend.
- `bazis audit` reviews the frontend too: `front_check`, `front_status`, the guides of
  bazis-front, and with `--fix` the generated files, `tsc`, lint, the tests and the
  end-to-end tests.
- `BAZIS_FRONT_REQUIREMENT` replaces the requirement of bazis-front in a new product (a
  path to a wheel or a checkout, or a URL), to try a version that is not on PyPI; uv
  builds it again (`--refresh-package`) instead of reusing the build of an older commit.
- **`bazis new` creates the database of the project.** After `.venv`, the settings of the
  project (`.env`, the `BS_DATABASES__DEFAULT__*` variables of the environment) are read
  by its Python and the database is created on PostgreSQL when it is missing, with the
  extension PostGIS for the PostGIS backend (the default); an existing one is kept. When
  PostgreSQL cannot be reached (5 seconds) or the database cannot be created, it says why
  and goes on. The task tells the agent what was done; the rules tell it never to drop or
  recreate the database and, after the first `migrate`, to add migrations instead of
  generating the applied ones again (every trial agent created the database itself, one
  dropped it to regenerate its migrations). The evals create it the same way.
- The rules of the agent: a package is added with its latest release as the minimum
  (`catalog_version` of `list_packages`); temporary files go to `.scratch/` of the project
  (in the `.gitignore` of the skeleton), not `/tmp`; no password or other secret in the
  messages or the summary, only where it is set; a database the agent creates is reported.
- The evals have a task with a frontend (`helpdesk`), graded on the specs against a fresh
  contract, the generated files, the build, the lint and component tests, and the
  end-to-end tests against the backend.

## Breaking changes

- `bazis new` needs Node.js 22.12 or newer with npm unless `--no-frontend`: without them
  it stops before writing anything.
- New projects need bazis 2.13.0 (the language of each request, `bazis.W004`, `W005`, the
  database checks of `bazis_doctor`), the latest release, which bazis-front also needs, and
  bazis-test-utils 2.5.0 (its pytest plugin) in `requirements-dev.txt`.
- bazis-cli and new projects need bazis-mcp 2.4.5 (the tools `front_check`,
  `front_status`, `front_catalog`, and the installed packages read from the Python of the
  project at every call: before, the server run by bazis-cli reported the packages of the
  Python of the CLI); a new product needs bazis-front.
